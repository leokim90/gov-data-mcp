# 운영 대시보드 + 오류 알림 설계

작성일: 2026-07-28
상태: 승인됨 (구현 대기)

## 배경

2026-07-28 gov-data MCP를 ONE finger 조직 커넥터로 배포했다(24석). 사내 게시판 공지를 앞두고 있으나 운영 가시성이 없다.

같은 날 발견된 나라장터 키워드 버그가 문제를 드러냈다. 그 버그는 **오류를 한 번도 내지 않았다.** 어떤 키워드로 조회해도 전체 목록이 반환됐고 `totalCount`만 이상했다. 팀원이 제보하지 않았으면 계속 몰랐을 것이다. 정부 API 스키마 변경 시 파싱이 조용히 빈 배열로 실패하는 기존 리스크와 같은 계열이다.

즉 필요한 것은 오류 감시만이 아니라 **조용한 실패 감지**다.

## 목표

1. "채택되고 있나"에 답한다 — 일별 호출 추세를 본다
2. 조용한 실패를 포함한 이상을 사람이 안 보고 있을 때도 알린다
3. 경량 원칙(의존성 추가 금지)과 graceful 계약을 깨지 않는다

## 비목표

- **사용자별 사용량 추적.** 조직 커넥터는 URL 1개를 24명이 공유하고 MCP 요청에 사용자 신원이 없다. 사람별 토큰으로 바꾸면 "클릭 한 번" 온보딩을 잃는다 — 편의를 택했다(2026-07-28 결정).
- 실시간 로그 스트리밍, APM, 분산 추적. 24명 규모에 과하다.

## 아키텍처

```
[MCP 도구 호출] → callTool 디스패처
                    ├→ metrics.record()  ── 메모리 집계
                    │      ├→ 5분마다 flush → /data/metrics.jsonl (하루 1줄)
                    │      └→ 임계 초과 시 → Slack webhook (즉시)
                    └→ 기존 usage.js (출처별 쿼터) — 역할 분리 유지

[GET /dashboard?t=관리자토큰] → self-contained HTML (30초 자동 새로고침)

[외부 스케줄(하루 1회)] → GET /healthz → 무응답이면 Slack
                          ※ 서버가 죽으면 서버는 알릴 수 없다 → 외부 감시 필수
```

알림 로직을 서버에만 두지 않는 이유가 이 마지막 줄이다. 서버 다운은 서버가 감지·통보할 수 없으므로 외부 감시가 논리적으로 필수다. 반대로 오류율·조용한 실패는 서버만 알 수 있으므로 서버에 둔다. 둘은 대체재가 아니라 상호 보완이다.

## 구성 요소

### 1. `src/core/metrics.js` (신규)

기존 `usage.js`는 **출처별 API 쿼터**를 센다. 이 모듈은 **도구별 품질 지표**를 센다. 관심사가 다르므로 파일을 나눈다.

도구마다 집계한다:

| 지표 | 목적 |
|---|---|
| `calls` | 호출 수 — 채택률 |
| `errors` | 예외·API 에러 응답 수 |
| `empty` | 결과 0건 수 — **조용한 실패 감지의 핵심** |
| `durationSum` | 평균 응답시간 산출용 (합계만 저장, 평균은 표시 시 계산) |

날짜 롤오버는 `usage.js`와 동일하게 KST 기준(`Intl.DateTimeFormat('sv-SE', { timeZone: 'Asia/Seoul' })`)으로 처리한다.

인터페이스:
- `record(tool, { ok, empty, durationMs })` — 호출 1건 기록
- `snapshot()` — 오늘 집계 반환 (대시보드·healthz용)
- `history(days)` — 저장된 과거 일자 반환 (대시보드 추세용)

### 2. 저장 — `/data/metrics.jsonl`

하루 한 줄 JSON. 5분 주기 flush + 프로세스 `SIGTERM` 시 flush.

```json
{"date":"2026-07-28","tools":{"fetch_nara_bids":{"calls":42,"errors":0,"empty":3,"durationSum":18400}},"sources":{"datago":128}}
```

하루 1줄이면 1년에 수십 KB다. 1GB 디스크로 사실상 무제한이므로 회전·삭제 정책을 두지 않는다.

**미검증 리스크:** Cloudtype 프리티어에서 디스크 볼륨 마운트가 가능한지 확인되지 않았다. 구현 1순위로 검증한다. 불가하면 폴백은 "외부 스케줄이 매일 `/healthz` 스냅샷을 워크스페이스 파일로 축적" — 대시보드는 그 파일 대신 서버 메모리만 보여주고, 추세는 워크스페이스 쪽에서 본다.

### 3. 대시보드 — `GET /dashboard?t=<토큰>`

서버가 self-contained HTML 문자열을 반환한다. 템플릿 리터럴로 만들며 템플릿 엔진을 추가하지 않는다(경량 원칙).

표시 항목:
1. 서버 상태 · 버전 · 가동시간
2. 오늘 호출 수 + 어제 대비 증감
3. 최근 14일 추세 (인라인 SVG 막대 — 차트 라이브러리 없이)
4. 도구별 표: 호출 / 오류 / 0건 / 평균 응답시간
5. 출처별 한도 소진 게이지 (datago 8000 · bizinfo 1000 · smes 1000)
6. 최근 오류 20건 (시각 · 도구 · 메시지)

**인증:** 기존 `tokenRegistry`를 재사용하되 `default` 라벨(관리자 토큰)만 통과시킨다. 부서 토큰은 403. 토큰 없으면 401. 대시보드는 전사 사용량이 보이므로 부서 토큰에 열지 않는다.

### 4. 알림 — Slack webhook

`SLACK_WEBHOOK_URL` 환경변수를 추가한다. **미설정 시 알림만 비활성화되고 서버는 정상 기동한다** — 키 미설정 시 graceful 폴백이라는 기존 계약과 동일한 태도다.

발송 조건:

| 조건 | 임계 | 감지 주체 |
|---|---|---|
| 오류율 급증 | 10분 이동창에서 오류율 30% 초과 (최소 5건 이상일 때만) | 서버 |
| 쿼터 소진 임박 | 출처별 한도 80% 도달 | 서버 |
| 조용한 실패 의심 | 특정 도구의 0건 비율이 당일 80% 초과 (최소 5건 이상일 때만) | 서버 |
| 서버 무응답 | `/healthz` 실패 | 외부 스케줄 |

**중복 억제:** 같은 사유는 1시간에 1회만 발송한다. 임계 근처에서 진동할 때 알림이 폭주하는 것을 막는다.

"최소 5건 이상일 때만" 조건은 호출이 적은 아침 시간에 1건 실패가 100% 오류율로 잡히는 오탐을 막는다.

정상일 때는 아무것도 보내지 않는다(기존 harness-sentinel과 동일 철학: 성공은 조용히, 실패는 시끄럽게).

### 5. 테스트 — `tests/metrics.test.js` (신규)

- 집계 정확성: calls/errors/empty/duration이 정확히 누적되는가
- KST 날짜 롤오버 시 리셋되는가
- 알림 중복 억제: 같은 사유 연속 발생 시 1회만 발송되는가 (webhook 모킹)
- 임계 미달(5건 미만)에서는 발송하지 않는가
- 대시보드 라우트: 무토큰 401, 부서 토큰 403, 관리자 토큰 200
- flush 후 재기동 시 이력이 복원되는가

기존 `tests/http-handshake.js`에 대시보드 인증 케이스를 추가한다.

## 단계

**1단계 — 계측 + 대시보드**
`metrics.js` + `callTool` 계측 + `/dashboard` 라우트 + 테스트. 이력 없이 "오늘"만 보여준다. 이것만으로 채택 여부와 오류 발생을 확인할 수 있다.

**2단계 — 저장 + 알림**
디스크 볼륨 검증 → `/data/metrics.jsonl` flush/복원 → 추세 그래프 → Slack webhook + 임계 판정 + 중복 억제 → 외부 생존 감시 스케줄.

1단계를 배포해 실제 트래픽을 본 뒤 2단계 임계값을 조정한다. 임계값은 실제 분포를 보기 전엔 추측이다.

## 가드레일 준수 확인

- 의존성 추가 없음 — HTML은 템플릿 리터럴, webhook은 내장 `fetch`, 차트는 인라인 SVG
- stdout 로그 없음 — 기존대로 stderr만
- 키/토큰 미설정 시 throw 금지 — `SLACK_WEBHOOK_URL` 미설정은 알림 비활성화로 처리
- `AUTH_TOKEN`(default 라벨) 하위호환 유지 — 대시보드 인증이 이 라벨에 의존
